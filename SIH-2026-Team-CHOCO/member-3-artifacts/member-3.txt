## 🎯 PROJECT OBJECTIVE

Build a complete, production-ready predictive analytics platform that helps law enforcement agencies proactively prevent cybercrime cash withdrawals. The system takes victim complaints, uses AI to predict where criminals will withdraw money, identifies mule accounts used for money laundering, and enables police to take preventive action through ATM verification triggers—all within minutes of the complaint being filed.

**Core Problem We're Solving:**
Currently, when a cybercrime complaint is filed, it takes 2-4 hours for police to coordinate with banks to freeze accounts. By that time, criminals have already withdrawn the money from ATMs. Our system reduces this response time to under 5 minutes by:
1. Instantly analyzing the complaint
2. Predicting which ATM the criminal will use
3. Triggering facial recognition/OTP verification at that ATM
4. Alerting nearby police officers
5. Identifying and freezing mule accounts


## 🏗️ SYSTEM ARCHITECTURE OVERVIEW

The system consists of 5 main layers:

**Layer 1: User Interfaces (3 Web Applications + WhatsApp Chatbot)**
1. Victim Complaint Portal (PWA) - For citizens to file complaints and track status
2. Police Command Center (Desktop Web) - For inspectors to investigate with heatmaps and LLM
3. Police Field Dashboard (Mobile-Responsive Web) - For constables to receive alerts on the go
4. WhatsApp Chatbot Integration - For anonymous tips, complaint status, and officer alerts

**Layer 2: API Gateway & Backend Services**
- FastAPI REST APIs for all CRUD operations
- WebSocket server for real-time updates
- Authentication & Authorization (JWT + Role-based access)
- Banking Switch API Mock (simulates Step-Up Verification trigger)

**Layer 3: AI/ML Engine (Runs on 2 GPU Machines)**
- Spatio-Temporal Transformer Model: Predicts ATM withdrawal locations with 85%+ accuracy
- Graph Neural Network (GNN): Detects and scores mule accounts in transaction networks
- Mule Scoring Algorithm: Rule-based overlay that scores accounts 0-100 based on suspicious patterns
- LLM Agent: LangChain + LLM for natural language database queries

**Layer 4: Data Layer**
- PostgreSQL: Stores victim PII, complaint metadata, user accounts
- Neo4j Graph Database: Stores relationships between victims, mules, ATMs, and complaints
- Redis: Caching, session storage, rate limiting
- IPFS: Decentralized storage for encrypted evidence files

**Layer 5: Blockchain Audit Layer**
- Hyperledger Fabric / Ethereum: Immutable audit trail of all actions
- Cryptographic hashing: Every evidence file, prediction, and action is hashed and stored on-chain
- Tamper-proof chain of custody: Complete case history from complaint to resolution


## 🔄 COMPLETE END-TO-END USER FLOW

**PHASE 1: VICTIM COMPLAINT (T+0 to T+2 minutes)**

The victim who lost money to a scam interacts with the system through TWO possible channels:

Channel A: Victim Complaint Portal (Web - PWA)
- Victim opens the portal on their phone or laptop
- Fills a simple 3-step complaint form (Personal Details → Fraud Details → Fraudster Details)
- Uploads screenshots, transaction proofs, and other evidence
- Submits the complaint and receives: "✅ Complaint #C1001 Registered"
- Gets a unique complaint reference number for tracking

Channel B: WhatsApp Chatbot (Quick, Anonymous Channel)
- Victim messages the official WhatsApp number
- The chatbot guides them through a conversational flow
- For anonymous tips, the chatbot offers complete confidentiality
- Victim provides details via text or voice notes
- System creates a complaint in the backend and provides a reference number
- Status updates are sent proactively via WhatsApp

**Key Features in Victim Portal:**
- Real-time status tracking with visual timeline (Submitted → Analyzing → Action Taken → Resolved)
- Push notifications for status changes via WhatsApp/Email/SMS
- Evidence upload with encryption before storage
- Multi-language support for regional accessibility
- PWA capability for offline submission and installation on home screen

**PHASE 2: AI ANALYSIS & PREDICTION (T+2 to T+5 minutes)**

As soon as the complaint is submitted, the backend triggers the AI/ML pipeline:

Step 2A: Spatio-Temporal Transformer Analysis
- The Transformer model analyzes the fraudster's historical withdrawal patterns
- Considers spatial factors (ATM proximity to metro stations, police stations, transport hubs)
- Considers temporal factors (time of day, day of week, fraud patterns)
- Factors in local traffic density and transit accessibility
- Output: Top 3 most likely ATM locations with probability scores (70%+ for top prediction)

Step 2B: Graph Neural Network Mule Detection
- The GNN traces funds through the transaction network
- Identifies the entire money trail: Victim → Primary Mule → Secondary Mule → ATM
- Each account is scored 0-100 based on suspicious patterns
- Accounts scoring 70+ are marked HIGH RISK for immediate freeze
- The system generates a visual graph showing the complete money trail

Step 2C: Integrated Output
- Merges ATM predictions with mule account data
- Determines if the predicted ATM is connected to high-risk mules
- If risk threshold is met, proceeds to Phase 3 automatically

**PHASE 3: AUTOMATED ACTIONS (T+5 to T+10 minutes)**

Based on the AI analysis, the system triggers automated actions:

Action 1: Step-Up Verification Trigger
- System calls the Banking Switch API Mock
- Requests: Enable Facial Recognition or OTP verification on the predicted ATM
- The API simulates a real banking network integration
- Accounts linked to high-risk mules are specifically flagged
- Verification remains active for the predicted withdrawal window (2-6 hours)

Action 2: Mule Account Freeze Alert
- System generates a freeze request letter automatically
- The request is sent to the Bank Nodal Officer via the system
- High-risk mule accounts are flagged for immediate freeze
- All freeze requests are logged on the blockchain for audit

Action 3: Police Alert Generation
- System sends a priority alert to the nearest police station
- Alert contains: ATM location, risk score, withdrawal window, connected mules
- Alert is pushed to the Police Field Dashboard in real-time
- Constables on duty receive the alert on their mobile dashboard

**PHASE 4: POLICE INVESTIGATION & ACTION (T+10 to T+30 minutes)**

Two types of police users interact with the system:

Police Command Center (Inspectors - Web Desktop):
- Inspector opens the Command Center dashboard
- Sees live heatmap of all high-risk ATMs in their jurisdiction
- Views the graph visualization showing the complete money trail
- Uses the LLM Agent to ask questions in natural language:
  "Show all high-risk ATMs in Indiranagar connected to investment fraud in the last 2 hours"
- Clicks on the predicted ATM to view full details
- Reviews the mule accounts and their scores
- Takes actions:
  → Trigger Step-Up Verification (if not auto-triggered)
  → Request Account Freeze for high-risk mules
  → Generate FIR Draft automatically
  → Dispatch patrol to the ATM location
- All actions are logged on the blockchain

Police Field Dashboard (Constables/Patrol - Mobile-Responsive Web):
- Constable opens the dashboard on their phone
- Sees active alerts pushed to their dashboard
- Alert card shows: ATM location, risk score, distance from officer's location, time to reach
- Constable can:
  → Navigate to the ATM using integrated maps
  → Mark "Patrol Dispatched" when en route
  → Mark "Verification Checked" upon arrival
  → Request backup if needed
- All actions update the complaint status in real-time

**PHASE 5: OUTCOME & FEEDBACK LOOP (T+30 minutes to T+2 hours)**

Success Scenario:
- Criminal attempts withdrawal at the predicted ATM
- Facial Recognition / OTP verification blocks the transaction
- Police arrive (or receive real-time alert)
- Mule accounts are frozen, money is recovered
- Complaint status updates to "RESOLVED"
- The system records this as a "Successful Prevention"

The Feedback Loop:
- Officer marks the case as "Successful Prevention"
- All data (predictions, actions, outcomes) is logged
- The system periodically (daily/weekly) retrains models with new data
- The model improves over time with real-world feedback
- This creates a self-improving AI system

**PHASE 6: SYSTEM ADMINISTRATION (Ongoing)**

Admin Management Panel (IT Team - Web Desktop):
- System Admins manage the entire platform
- Key capabilities:
  → User Management: Add/remove/update police officers and admins
  → Role Assignment: Assign roles (Inspector, Constable, Admin)
  → System Health Monitoring: CPU, RAM, GPU, Disk, Network usage
  → Model Performance: View accuracy, precision, recall metrics
  → Audit Logs: View all actions taken in the system (blockchain-backed)
  → Complaint Overview: See all complaints, their status, and resolution times
  → Evidence Management: Access and verify stored evidence

## 🧠 LLM AGENT & CHATBOT SYSTEM

**LLM Agent (Advanced - For Inspectors)**
- Purpose: Allow investigators to query the graph database in natural language
- Technology: LangChain + GPT-4/Claude/LLaMA
- How It Works:
  1. Officer types a question: "Show all high-risk ATMs in Indiranagar connected to investment fraud in the last 2 hours"
  2. LLM understands the intent and extracts: Location, Risk Level, Time Frame, Fraud Type
  3. LLM generates a Cypher query for Neo4j: MATCH (c:Complaint)-[:CONNECTED_TO]->(a:ATM) WHERE c.type = "Investment" AND c.time > datetime() - 2h AND a.location = "Indiranagar" AND a.risk_score > 70 RETURN a.id, a.risk_score, COUNT(c) as complaint_count
  4. Query executes on Neo4j
  5. Results are formatted as natural language with visualizations
  6. Response includes: Data + Charts + Recommendations + Action Buttons
- Key Features:
  * Handles complex multi-hop queries
  * Understands police-specific terminology
  * Provides visual results (graphs, charts, maps)
  * Suggests follow-up queries
  * Saves frequently used queries as templates

**Integrated Chatbot (Simple - For All Users)**
- Purpose: Help users navigate the system and answer FAQs
- Technology: RAG (Retrieval-Augmented Generation) + Vector Database
- How It Works:
  1. User asks: "How do I trigger Step-Up Verification?"
  2. System searches a knowledge base of FAQs and documentation
  3. Retrieves the most relevant answer
  4. Returns a concise, helpful response
- Key Features:
  * Pre-built FAQs: "What is a mule account?", "How does the predictive model work?"
  * Suggestion chips for quick answers
  * Feedback buttons: "Did this help? Yes/No"
  * Escalates complex queries to the LLM Agent
- Target User: All system users (officers, victims, admins)

**WhatsApp Chatbot (Communication Channel)**

## 📊 DATABASE & BLOCKCHAIN ARCHITECTURE

**PostgreSQL (Relational Database)**
- Purpose: Store all structured, relational data
- Tables: Users, Complaints, Evidence Metadata, User Roles, Audit Logs
- Security: All PII is encrypted at rest (AES-256)
- Key Tables:
  * users: id, name, role, station, phone, email, hashed_password
  * complaints: id, victim_name, phone, amount, fraud_type, fraudster_upi, fraudster_phone, status, created_at
  * evidence: id, complaint_id, file_hash, ipfs_cid, file_type, uploaded_at
  * actions: id, complaint_id, action_type, initiated_by, status, created_at

**Neo4j (Graph Database)**
- Purpose: Store relationships between entities for money trail analysis
- Nodes: Victim, Mule, ATM, Complaint, Phone_Number, UPI_ID, Bank_Account
- Relationships: SENT_MONEY_TO, TRANSFERRED_TO, WITHDREW_AT, CONNECTED_TO
- Key Queries:
  * Find shortest path between victim and ATM
  * Identify all mule accounts connected to a complaint
  * Find ATMs with the most connected complaints
  * Detect patterns in money laundering networks
- Mule Scoring: Each node has a "mule_score" property (0-100) calculated by the algorithm

**Redis (Caching & Sessions)**
- Purpose: Speed up frequently accessed data
- Cache: ATM predictions, user sessions, rate limiting
- Pub/Sub: Real-time WebSocket message distribution

**IPFS (Decentralized Storage)**
- Purpose: Store encrypted evidence files
- How It Works:
  1. File uploaded → AES-256 encrypted
  2. Encrypted file → Uploaded to IPFS
  3. IPFS CID (Content Identifier) → Stored in PostgreSQL
  4. File hash → Stored on blockchain for verification
- Benefits: Immutable, censorship-resistant, content-addressed

**Blockchain (Hyperledger Fabric / Ethereum)**
- Purpose: Immutable audit trail for legal admissibility
- What's Stored:
  * Complaint submission timestamp (cryptographic proof of existence)
  * Evidence file hashes (proof of integrity)
  * AI predictions and triggers (proof of proactive action)
  * Police actions (proof of chain of custody)
  * Resolution status (complete case history)
- Why It Matters: Digital evidence must be tamper-proof for court admissibility
- Implementation: Only hashes are stored, not full data (to save cost and maintain privacy)


## 🔒 SECURITY ARCHITECTURE

**Authentication**
- JWT-based authentication for all web interfaces
- OTP-based login for Victim Portal (phone number + OTP)
- Government ID + Password for Police Command Center
- Biometric + Password for Police Field Dashboard (optional)
- Session expiration: 8 hours for admins, 4 hours for officers

**Authorization (Role-Based Access)**
- Admin: Full access to all features and user management
- Inspector: Access to Command Center, LLM Agent, all complaints
- Constable: Access to Field Dashboard, ATM alerts, limited complaints
- Victim: Read-only access to their own complaint and status

**Data Encryption**
- All victim PII is encrypted at rest (AES-256)
- All data is encrypted in transit (TLS 1.3)
- Evidence files are encrypted before IPFS upload
- Passwords are hashed with bcrypt (salt rounds: 12)

**API Security**
- Rate limiting: 100 requests per minute per user
- CORS: Only allowed origins
- Input validation: All API inputs validated with Pydantic/Zod
- SQL/NoSQL injection prevention: ORM/parameterized queries
- XSS prevention: Content Security Policy (CSP) headers
